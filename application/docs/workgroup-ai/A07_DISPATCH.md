## 核心设计：接受一次派发是一串拒绝

本模块是**网络消息能导致本机运行**的唯一入口，因此写成"拒绝序列"而非"步骤序列"。这里不假设 Hub 已经检查过什么：本地需要的每个事实，要么再次向 Hub 核实，要么在本地确立。**"值得信任的 Hub"是这个文件承担不起的假设**，因为它的失败形态是同事的 Bot 带着别人的授权在跑。

顺序是刻意的，每一步都有自己的拒绝：

1. **设备必须是凭据铸造时的设备**——在出示 nonce **之前**检查。否则一个发给别设备的帧会消耗掉本设备凭据，把真正执行者还需要的东西烧掉（有断言：`consumed === false`）。
2. **nonce 只出示一次**——出示即标记消耗，所以重放必须在调用之前被拦下，否则第二次派发会在第一次旁边起一个。
3. **目录必须真实、绝对、且位于已批准根内**——在**解析后**的路径上判断，因此根内指向外部的符号链接会被抓住。
4. **任务必须在批准且未被撤销的状态**——本地记录的 revocationVersion 先比对，网络都不发。

**本模块不运行任何东西**：它返回一个决定，由调用方打开 Session。这个切分让接受规则可以脱离 Session、模型与进程被测试。

## 目录校验：为什么每条都在

| 检查 | 若不检查会怎样 |
|---|---|
| 绝对路径 | 相对路径会相对"进程恰好从哪启动"解析，员工手动启动与服务启动结果不同 |
| 存在且是目录 | 直接创建等于凭空发明一个 owner 从未批准的工作区 |
| **realpath 在根内** | 只比对未解析字符串会放行根内指向外部的符号链接——正是需求点名的逃逸 |
| 不是文件系统根 | 接受 `/` 会让其余所有检查失去意义 |
| 带分隔符的前缀比较 | `work-other` 与 `work` 共享前缀；不带分隔符的 `startsWith` 会把兄弟目录当成在根内。**有专门用例** |

## 设计要点

| 决定 | 理由 |
|---|---|
| 目录校验在 consume **之前** | 跑不了的派发不该烧掉凭据：owner 修好路径后同一凭据仍可用 |
| 空工具列表保持为空而非放宽 | "未批准任何工具"是对全部工具的拒绝，不是对任意工具的许可 |
| consume 返回的 scope 优先于本地 scope | Hub 记录的是权威；本地只是应对 Hub 响应缺字段的兜底 |
| 每个拒绝码对应不同处置 | 缺目录、路径不可用、越界、已撤销是四件不同的事，员工要做的事也不同 |
| 纯校验用例不依赖 Hub | 本地检查必须在没有网络时同样安全——"离线所以放行"是最糟的失败形态 |
