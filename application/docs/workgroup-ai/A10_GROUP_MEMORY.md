## 达成条件

| 条件 | 结果 |
|---|---|
| 可追溯 | 通过：条目记录作者、修订号、是否引用消息、引用哪一条；无引用时**明说** unsourced |
| 可纠错 | 通过：修订产生 revision 行，**前后两版文本都留在历史里**，修订人与时间可查 |
| 可删除 | 通过：删除后不再出现在检索中、按 id 也读不到；**修订轨迹对当前成员仍可读**（见下） |
| 授权 Bot 检索 | 通过：Bot 以其 owner 的凭据检索，每个条目带 `retrievedAs` |
| 非成员不可检索 | 通过：房间/搜索/写入/读取/历史全部 404；**被移除的成员一并失去** |

## 三个刻意的设计

### 1. Bot 不是第二个主体

Bot 以**其 owner 的凭据**检索，Hub 按 owner 授权，返回什么就是什么。本模块**没有**"以 Bot 身份读取"的代码路径——那样的路径会是一种 Hub 从未签发过的授权。每个条目带 `retrievedAs`，因此 Bot 在群里引用记忆时能说"我是以 Alice 的身份读到的"，而读者能核对 Alice 是否读得到。

### 2. 客户端不自己过滤权限

客户端原样传递 Hub 返回的内容。客户端过滤会成为**第二套、更弱的权威**，而它错误放行的条目看起来与Hub 允许的条目一模一样——这正是静默泄漏的形态。

### 3. 删除后修订轨迹仍然可读（Hub 的刻意设计）

按 id 读已删除条目返回 404，但 `/revisions` 对**当前成员**仍然可用：群能看到"有东西被删了、是谁删的"。轨迹是**决定的记录**，不是条目的文本——这正是丢失条目却不必丢失轨迹的原因。非成员依然拿不到。

## 与 Hub 契约对齐过程中修正的假设

| 我最初的假设 | 实际契约 | 处理 |
|---|---|---|
| 一条记忆有"当前版 + 历史版"两行 | 只有**修订**才写历史行；创建不写 | 断言改为"一次修订 = 一行，该行携带 previousBody 与 newBody" |
| 删除后仍可按 id 读到墓碑 | `readMemory` 对已删除条目返回 `undefined` → 404 | 断言 404，并说明"已删除"这一事实记在审计而非人人可读的墓碑上 |
| 空文本/空查询会同步抛错 | 这些方法都是 `async`，早期 `throw` 表现为 **rejection** | 断言改为 `rejects`，并写明这个区别对调用方 `try { await }` 的意义 |
| 删除后历史也应 404 | Hub 刻意让**当前成员**仍可读轨迹 | 断言改为"成员可读、非成员 404"，并记录这是更好的行为 |

第四条是本次唯一一处**我的假设比产品更差**的地方；其余三条是契约细节。

## 设计要点

| 决定 | 理由 |
|---|---|
| `citeMemory` 在代码里生成，不交给提示词 | 同样的措辞无论由什么产生都一致；无来源就写 unsourced，**绝不编造** message id |
| 过期条目**呈现**而非隐藏 | "直到三月为止的答案"往往正是读者要的；隐藏它会让读者无法区分"从没记过"与"记过但改了" |
| `live` 取自 Hub 而非本地重算 | 两套"是否仍有效"的实现，就是客户端显示已过期条目而 Hub 拒绝返回的原因 |
| scope 仅 `room` / `author` 两种，断言与 Hub 一致 | 客户端自造词汇会发出 Hub 拒绝的请求，而报错没人能处理 |
| 跨房间引用被拒绝 | 那会让成员引用他读不到的边界之外的内容 |
