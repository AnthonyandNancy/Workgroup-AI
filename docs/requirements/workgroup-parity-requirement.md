# 本轮确认结论

1. **基线版本**
   - 以当前仓库中的原版群聊代码为唯一基线，不另找上游版本。

2. **功能范围**
   - 包括原群聊的全部功能。
   - 与原群聊冲突、无法直接照搬的功能，以工作群模型为主。

3. **样式标准**
   - 原群聊已有的界面，工作群必须与之一模一样。
   - 工作群新增功能的外观和交互，必须与原群聊类似，不能形成第二套视觉体系。

4. **当前缺口**
   - 现工作群功能不完整。
   - “不能拉机器人”只是其中一个已确认缺口，其他缺口需要按当前代码逐项核对。

5. **解散权限**
   - 只有工作群群主和 Hub 管理端可以解散。
   - 工作群管理员不能解散，普通成员不能解散。

6. **Hub 管理端边界**
   - Hub 管理端是绑定在 `server/` 内的 Web 管理后台，入口为 `/admin/`。
   - 它不是独立项目、独立前端服务或第三个运行进程。
   - 部署 `server/` 即同时部署 Hub API、实时服务和管理后台。
   - 因此 Hub 管理端相关修改属于服务端修改，不改变“`application/` + `server/` 两个代码/运行边界”的架构。

7. **客户端实现方式**
   - 工作群不是通过修改原群聊代码来适配的。
   - 工作群是复制原群聊的功能、页面结构、样式和交互，新建为独立的工作群实现，再在工作群复制件上增加工作群专属能力。
   - 原群聊的代码、样式、行为和测试保持不变，不能在工作群改造中改动。

# 代码隔离原则

**【已确认】工作群采用“复制后独立演进”的方式实现。**

1. **复制来源**
   - 以当前仓库原版群聊代码为复制来源。
   - 复制范围包括原群聊的功能、页面结构、样式、交互和必要的配套实现。

2. **新建工作群实现**
   - 复制后形成工作群自己的实现。
   - 工作群专属能力，包括 Hub 状态、审批、任务、Bot 成员、群记忆和离线状态，只加在工作群复制件中。

3. **原群聊代码不改**
   - 不在原群聊代码中增加工作群判断分支。
   - 不通过修改原群聊的页面、样式或交互来适配工作群。
   - 不把工作群专属状态写入原群聊的数据结构或行为路径。

4. **原群聊行为不变**
   - 原群聊的创建、消息、成员、设置、详情、侧栏和删除/归档保持原行为。
   - 工作群复制件的改动不能反向影响原群聊。

5. **后续维护边界**
   - 复制完成后，工作群与原群聊分别独立演进。
   - 原群聊后续升级是否同步到工作群，另行确认；本次不以“共享同一份代码”为方案。

# 背景

## 产品原始定位

**【已确认】** 实施书要求：

- 工作群以原版 DS Bot 群聊 UI、组件、样式和交互为基准；
- 原版普通群聊完整保留，与工作群互不干扰；
- 工作群在复刻原群聊的基础上增加跨用户协作能力；
- 不允许另起一套群聊 UI。

## 当前实际状态

**【核验】当前工作群与要求存在结构性差距，不是细节偏差。**

当前工作群虽然能显示 Hub 群、消息、成员、审批和任务，但：

- 主聊天区、消息展示、输入区、成员区、设置页、详情页均为工作群自有界面；
- 仅共用了原版房间头像和部分设计变量，没有以原群聊代码复制件为基础实现完整页面结构；
- 因此用户看到的工作群与原群聊“没有相似感”是结构性结果，不是配色或间距微调可以解决。

**【核验】“拉机器人”确实不存在。**

当前工作群：

- 成员设置只支持按用户 ID 邀请真人；
- 没有“添加 Bot”“拉入 Bot”“移除 Bot”的入口；
- 工作群中显示的 Bot 是从所有真人成员已公开的 Bot 自动汇总出来的，不是明确的群 Bot 成员；
- 没有“把某个 Bot 加入本群”的业务动作。

**【核验】当前工作群还缺少以下原群聊能力或对应入口：**

| 核验项 | 当前事实 | 需求结论 |
|---|---|---|
| 创建工作群 | 直接创建并自动生成日期名称，没有原群聊式创建表单 | 必须补齐原群聊式创建流程 |
| 群名称、群公告 | 仅支持改名，没有群公告 | 必须补齐 |
| 管理员 | 只有工作群真人角色，没有原群聊“管理员 Bot”设置 | 按工作群角色模型改造，不设可代替审批的 Bot 管理员 |
| 添加/移除 Bot | 不存在 | 必须补齐 |
| 成员列表 | 自有胶囊式列表，没有原群聊成员详情、工作状态和停止成员工作 | 必须对齐 |
| 群设置 | 自有设置页，缺少公告、谁应答、工作目录、权限、管理员、添加 Bot、侧栏置顶/隐藏 | 必须按原群聊结构补齐或按工作群规则明确适配 |
| 群详情 | 没有原群聊的群概览、成员工作状态、停止成员、用量等详情区 | 必须对齐 |
| 消息展示 | 自有消息气泡，没有以原群聊代码复制件实现消息组件 | 必须对齐 |
| 输入区 | 自有输入框和附件按钮，没有原群聊输入区的完整交互 | 必须对齐 |
| `+` 菜单 | 没有“添加文件 / 引用会话 / 定时任务”菜单 | 必须补齐，并适配工作群权限 |
| 图片 | 附件以文件按钮呈现，没有原群聊图片消息展示 | 必须对齐 |
| 群记忆 | 客户端已具备读取能力，但工作群界面没有群记忆入口 | 必须补齐界面和操作 |
| 侧栏 | 工作群作为独立会话存在，没有以原群聊代码复制件实现群会话行、置顶/隐藏、未读和审批提示 | 必须对齐 |
| 轮次/群内工具 | 未实现，旧文档曾列为非目标 | 按“工作群优先”改为审批任务、任务进度和群记忆，不自动跨设备执行 |
| 解散 | 客户端仅群主可解散，服务端仅群主可解散，Hub 管理端可解散；管理员不能解散 | 权限结论正确；要求两条解散路径结果完全一致 |

**【核验】解散路径存在一致性缺口。**

当前群主从客户端解散时，会撤销待处理邀请并取消未完成任务；Hub 管理端解散路径目前没有执行同样的未完成任务取消。业务上必须统一，不能出现“群主解散后任务停止，Hub 管理端解散后任务仍可审批”的差异。

> 本轮为当前仓库源码级核验；真实 UI 逐项点击和像素级截图对照仍需在后续验收中完成，不能把源码核对当作 UI 验收通过。

# 目标

**【已确认】本需求完成后，应达到以下结果：**

1. **工作群和原群聊属于同一个产品**
   - 用户打开工作群时，看到的是原版群聊的页面结构、消息样式、输入方式、成员区、设置和详情交互，而不是另一个独立工具。

2. **原群聊功能全部有对应实现**
   - 以当前仓库原版群聊代码为基线逐项核对；
   - 每一项原群聊功能都必须有明确结果：直接复刻、按工作群模型适配、或因安全冲突替换；
   - 不允许静默缺失。

3. **工作群专属能力完整**
   - 拉入/移除 Bot、Hub 状态、远程 Bot 审批、任务协作、成果分享、群记忆、断线补偿、群主/Hub 解散等能力完整可用；
   - 专属能力融入原群聊同一套视觉和交互，不形成第二套产品。

4. **样式达到明确标准**
   - 原群聊已有界面在相同渲染条件下与工作群一模一样；
   - 工作群新增界面与原群聊风格、布局逻辑、控件和反馈一致。

5. **普通群聊完全不受影响**
   - 原群聊的创建、聊天、成员、设置、历史、删除/归档及数据保持原样。

# 用户角色与场景

| 角色 | 使用场景 | 进入位置 | 操作 | 结果 |
|---|---|---|---|---|
| 工作群普通成员（真人） | 日常协作 | Bot 内部工作群会话 | 发消息、@、回复、引用、上传图片/附件、查看任务、检索群记忆 | 获得与原群聊一致的聊天体验 |
| 工作群群主（owner） | 建群、管理群、解散群 | 工作群设置/成员管理 | 邀请、移除、设置管理员、修改资料、拉入/移除 Bot、解散 | 工作群保持可管理，解散仅群主和 Hub 可执行 |
| 工作群管理员（admin） | 协助管理群 | 工作群设置/成员管理 | 邀请、移除、改角色、修改群资料 | 可管理群，但不能解散 |
| 被邀请人（真人） | 收到邀请后决定加入 | 邀请通知/工作群入口 | 接受或拒绝 | 接受后成为成员；拒绝或过期不获得访问权 |
| Bot 所有者（真人） | 把自己的 Bot 拉入工作群，或收到别人 @ 自己 Bot 的任务 | 工作群成员管理/审批区 | 拉入自己的 Bot、批准/拒绝任务、选择执行 Bot、撤销授权、复核成果 | Bot 作为群成员参与，但执行仍由所有者控制 |
| Bot 成员（非人类） | 代表所有者参与群聊和任务 | 被拉入工作群后出现在成员列表 | 被 @ 时产生待审批任务；在授权范围内执行 | 不具群管理权，不能代替所有者审批 |
| Hub 管理端管理员 | 运营管理、违规处理、解散工作群 | Hub 管理端 `/admin/` | 查询工作群、执行解散 | 解散结果与群主解散一致 |
| 原群聊用户 | 继续使用原版普通群聊 | Bot 内部原群聊入口 | 原群聊全部操作 | 完全不受工作群改造影响 |

# 核心功能

## 功能 1：入口、群会话行与打开

- **原群聊要求**：从 Bot 内部新建菜单进入，群会话在 Bot 内部以原群聊会话行呈现，支持置顶、隐藏、未读和审批提示。
- **工作群要求**：
  - “创建工作群聊”位于“创建群聊”正下方；
  - 工作群不出现在 DSH 一级导航；
  - 工作群在 Bot 内部打开，并使用从原群聊代码复制后形成的工作群会话行、头像、名称、预览、置顶/隐藏、未读和状态提示；原群聊会话行代码保持不变；
  - 工作群必须有清晰的工作群标识和 Hub 在线/离线状态。
- **最终结果**：用户像打开普通群聊一样打开工作群，不需要学习第二套导航或列表。

## 功能 2：创建工作群

- **原群聊要求**：创建时选择管理员、成员，填写名称；创建成功后进入群聊。
- **工作群要求**：
  - 创建工作群的界面结构与视觉必须复刻原群聊；
  - 必须提供群名称输入，不能只自动生成日期名称；
  - 创建者成为工作群群主；
  - 真人成员通过邀请加入，被邀请人接受后才成为成员；
  - 创建时可选择自己拥有的 Bot 加入；他人 Bot 需要 Bot 所有者授权；
  - 创建成功后打开工作群并出现在原群聊式会话行中。
- **最终结果**：用户看到的是原群聊式创建流程，只是成员关系按工作群邀请模型执行。

## 功能 3：消息展示与输入

- **原群聊要求**：消息气泡、消息堆叠、发送者显示、输入框、发送按钮、空状态、加载状态、错误状态和消息历史均按原群聊表现。
- **工作群要求**：
  - 基础消息界面必须以原群聊代码复制件为基础，保持原有页面结构、气泡、排版和交互；原群聊代码不改；
  - 消息按 Hub 的群内顺序展示；
  - 发送失败保留草稿并显示“未送达”；
  - 重复发送同一条消息不产生重复；
  - 支持图片和附件的原群聊式展示。
- **最终结果**：工作群的聊天主体在视觉和操作上与原群聊一致。

## 功能 4：输入区 `+` 菜单

- **原群聊要求**：输入区 `+` 菜单包含添加文件、引用会话、定时任务等入口。
- **工作群要求**：
  - 保留相同的入口位置和交互；
  - 添加文件按工作群附件权限处理；
  - 引用会话只能引用自己有权读取的数据；他人私人会话默认拒绝；
  - 定时任务不得绕过工作群审批；只能生成普通消息或待审批任务，不能定时直接执行远程 Bot。
- **最终结果**：用户能在工作群使用原群聊式输入工具，但不会越权读取或执行。

## 功能 5：@、回复与引用

- **原群聊要求**：支持 @ 成员、回复消息、引用会话，且提及与显示名解耦。
- **工作群要求**：
  - @ 使用稳定身份，显示名变化不改变提及对象；
  - @ 远程 Bot 只生成待审批任务，不直接执行；
  - 回复目标必须属于同一工作群；
  - 引用他人会话需数据所有者授权；
  - 提及选择器的外观和交互与原群聊一致。
- **最终结果**：用户能完成原群聊的协作动作，同时不突破工作群权限边界。

## 功能 6：成员管理与拉入 Bot

- **原群聊要求**：成员列表、管理员设置、添加/移除成员、成员状态。
- **工作群要求**：
  - 成员列表同时展示真人和 Bot；
  - 真人显示在线状态，Bot 显示其所有者；
  - 提供“拉入 Bot”“移除 Bot”入口，位置和交互与原群聊添加/移除成员一致；
  - 用户可直接拉入自己拥有的 Bot；
  - 拉入其他成员的 Bot 必须取得 Bot 所有者同意，不能由群主或管理员强行拉入；
  - 移除 Bot 后，该 Bot 不再可被 @、不再接受新任务；
  - Bot 所有者退出或被移除时，其 Bot 不再作为群成员参与新任务。
- **最终结果**：工作群可以像原群聊一样管理 Bot 成员，但 Bot 所有权和审批边界不被绕过。

## 功能 7：群设置

- **原群聊要求**：群名称、群公告、谁应答、工作目录、权限、成员与管理员、侧栏置顶/隐藏、群管理。
- **工作群要求**：
  - 设置页面的结构、分组、控件和确认交互与原群聊一致；
  - 原群聊设置项按工作群模型处理：

| 原群聊设置项 | 工作群处理 |
|---|---|
| 群名称 | 复刻 |
| 群公告 | 复刻 |
| 管理员 | 原群聊管理员是 Bot；工作群不设可代替所有者审批的 Bot 管理员，群管理由人类群主/管理员承担 |
| 成员与管理员 | 复刻成员管理结构；成员包含真人和 Bot |
| 添加/移除 Bot | 复刻入口；按 Bot 所有权和授权规则执行 |
| 谁应答 / 群轮次 | 不自动执行远程 Bot；如保留设置入口，只能影响展示或任务候选，不能触发执行 |
| 工作目录 | 不设跨用户共享的群级目录；由 Bot 所有者在任务审批时确定 |
| 权限 | 不设跨用户共享的群级执行权限；由任务审批范围决定 |
| 侧栏置顶/隐藏 | 复刻 |
| 删除/解散 | 工作群使用“解散”，历史保留；仅群主和 Hub 管理端可执行 |

- **最终结果**：用户在原群聊式设置界面中管理工作群，所有与安全冲突的设置都有明确、可见的工作群语义。

## 功能 8：群详情与成员工作状态

- **原群聊要求**：群详情包含群公告、成员列表、成员工作状态、停止成员工作、谁应答、权限、用量等。
- **工作群要求**：
  - 提供与原群聊结构一致的群详情区域；
  - 展示公告、成员、成员工作状态、任务进度、用量；
  - “停止成员工作”按工作群任务规则映射为取消任务或停止授权，不能直接跨设备结束他人本地进程；
  - 群记忆入口放在原群聊对应的位置。
- **最终结果**：工作群详情在结构上与原群聊一致，工作群专属状态有明确落点。

## 功能 9：远程 Bot 任务与审批

- **触发**：成员 A 在工作群 @ 成员 B 的 Bot。
- **工作群要求**：
  - 只生成待审批任务，不提前读取 B 的私人数据、不执行 B 的模型或工具；
  - 只有 B 本人可以批准或拒绝；
  - 群主、管理员和其他成员不能代批；
  - B 可选择已有 Bot、由 Chief 自动选择 Bot，或新建专用 Bot；
  - B 可设定目录、工具、时限和成果接收人；
  - 撤销后新的工具调用、重试和成果发布全部拒绝。
- **最终结果**：工作群能发起远程协作，但执行权始终属于 Bot 所有者。

## 功能 10：任务状态、取消、复核与分享

- **工作群要求**：
  - 按任务状态机展示待审批、已批准、排队、执行中、待复核、已完成、已分享等状态；
  - 群内只同步脱敏进度；
  - 取消后停止后续执行；
  - 成果只分享给批准范围内的人；
  - 终态任务不能恢复执行，新执行必须生成新任务和新审批。
- **最终结果**：成员能看见任务推进，但看不到不该看到的私人执行细节。

## 功能 11：群记忆

- **原群聊要求**：群记忆可检索、可修订、可纠错。
- **工作群要求**：
  - 提供与原群聊一致的群记忆入口和交互；
  - 保留来源、作者、访问范围、修订历史和有效期；
  - 非成员和被移除成员不能检索；
  - 授权 Bot 只能按批准范围检索；
  - 删除后保留必要修订轨迹；
  - 旧私人 Bot 记忆和普通群历史不自动并入。
- **最终结果**：工作群具备可追溯、可纠错的共享记忆，且不泄露私人记忆。

## 功能 12：Hub 状态、离线与恢复

- **工作群要求**：
  - 显示在线、重连中、离线状态；
  - Hub 离线时普通群聊、私人聊天和本地 Bot 继续工作；
  - 工作群未确认送达的消息不能显示为成功；
  - 重连后按顺序补拉，不重复、不乱序；
  - 失败时保留草稿和未发送状态。
- **最终结果**：用户能区分本地功能正常和工作群暂不可用。

## 功能 13：解散工作群

- **工作群要求**：
  - 只有工作群群主和 Hub 管理端可以解散；
  - 工作群管理员、普通成员不能解散；
  - 解散需要明确确认；
  - 解散后撤销待处理邀请；
  - 解散后取消未完成任务，未完成任务不得继续审批或执行；
  - 历史消息、任务、审批、群记忆保留并可只读访问；
  - 解散后不能继续发送消息、邀请成员、修改设置或发起新任务；
  - 群主解散和 Hub 管理端解散的业务结果必须完全一致。
- **最终结果**：解散权限和结果都清晰，不会出现“客户端已解散、Hub 仍可操作任务”的不一致。

## 功能 14：专属元素统一呈现

- **工作群要求**：
  - Hub 状态、审批卡、任务进度、Bot 所有者、角色、群记忆等专属元素使用原群聊的设计语言；
  - 专属元素是增量加入，不替换原群聊基础框架；
  - 不形成独立的配色、导航、控件或交互动效体系。
- **最终结果**：工作群是原群聊的独立复制和扩展，不是第二个群聊产品，也不依赖修改原群聊代码。

| R5 | 工作群新增功能与原群聊风格类似，不形成第二套视觉体系 |
| R6 | 普通群聊与工作群是两个不同实体，不能合并数据、权限或会话身份 |

| R16 | 原群聊的工作目录、权限等群级执行设置不能直接变成工作群跨用户共享权限；工作群按任务审批范围确定 |
| R17 | 原群聊的自动轮次、@ 直接执行、群内工具读取本机等行为，与跨用户安全冲突，按工作群优先改为待审批任务、任务进度和群记忆 |
| R18 | 定时任务不得绕过审批；只能定时发送消息或生成待审批任务 |
| R19 | 只有 Bot 所有者本人可以批准或拒绝其 Bot 的任务 |
| R20 | 任务终态不可恢复执行；新执行必须生成新任务和新审批 |
| R21 | 只有群主和 Hub 管理端可以解散工作群；工作群管理员不能解散 |
| R22 | 群主解散与 Hub 管理端解散必须撤销邀请、取消未完成任务、保留历史，并广播相同结果 |
| R23 | Hub 离线不得把未确认送达的消息显示为成功 |
| R24 | 历史工作群数据升级后必须保留；当前已可见的 Bot 不得因引入明确 Bot 成员关系而静默消失 |
| R25 | 原群聊的入口、创建、消息、成员、设置、历史、侧栏和删除/归档行为保持不变 |

# 状态与生命周期

## 工作群

```text
存续（Active）
├── 群主解散 ──────────────┐
└── Hub 管理端解散 ────────┤
                           ▼
                    已解散（Dissolved）
                    历史保留、只读
```

- **初始状态**：创建成功后进入存续。
- **允许解散者**：群主、Hub 管理端。
- **禁止解散者**：工作群管理员、普通成员、Bot。
- **终态**：已解散；不允许恢复发送、邀请、修改设置或发起任务。
- **是否允许恢复**：当前按不可恢复处理；如需恢复，另行确认。

## 邀请

```text
待处理 → 接受 → 成为成员
       → 拒绝 → 已拒绝
       → 过期 → 已过期
       → 群解散 → 已撤销
```

## Bot 成员

```text
未加入 → 所有者授权/本人加入 → 已加入
       → 移除/所有者退出 → 已移除
```

- Bot 加入后出现在成员列表，可被 @。
- Bot 被移除或所有者退出后，不再接受新任务。
- 正在执行的任务按撤销/取消规则处理。

## 任务

```text
待审批
├── 拒绝 → 已拒绝
├── 过期 → 已过期
└── 批准 → 已批准 → 排队 → 执行中
                         ├── 取消中 → 已取消
                         ├── 失败 → 已失败
                         └── 待复核 → 已完成 / 已分享
```

- 终态不可恢复执行。
- 群解散时，未完成任务必须取消。

## Hub 连接

```text
在线 ↔ 重连中 ↔ 离线
```

- 由网络和 Hub 可达性触发。
- 离线时工作群受限；普通群聊、私人聊天和本地 Bot 不受影响。

# 服务端影响

## Hub 管理端边界

**【已确认】Hub 管理端没有变成独立项目或独立进程。**

| 部分 | 位置/行为 |
|---|---|
| 管理后台页面 | `server/web/admin/` 静态资源 |
| 管理后台入口 | Hub 启动后提供 `/admin/` |
| 管理后台接口 | `server/src/api/admin.js` 提供 `/api/v1/admin/*` |
| 管理后台鉴权 | Hub 服务端统一处理 |
| 部署方式 | 部署 `server/` 即同时部署 Hub API、实时服务和管理后台 |

因此：

- Hub 管理端页面属于服务端内置 Web 后台；
- Hub 管理端调用的接口和业务规则属于服务端；
- 本次对 Hub 解散行为的一致性修正属于服务端修改；
- 不新增第三个代码/运行边界。

## 服务端修改判断

| 需求点 | 是否修改服务端 | 说明 |
|---|---|---|
| 拉入/移除 Bot | 必须 | 当前服务端只有真人成员关系，Bot 只是目录汇总，没有群 Bot 成员关系 |
| Bot 所有者授权 | 必须 | 是否允许拉入他人 Bot 必须由 Hub 判断，不能只靠客户端隐藏按钮 |
| Bot 加入/移除事件 | 必须 | 成员列表、@ 候选和任务目标需要实时更新 |
| 群公告 | 必须 | 当前房间没有公告字段和接口 |
| Hub 管理端解散一致性 | 必须 | 当前 Hub 管理端解散未执行与群主解散相同的未完成任务取消 |
| 既有工作群 Bot 可见性迁移 | 必须 | 引入明确 Bot 成员关系后，不能静默移除当前可见 Bot |
| 侧栏置顶/隐藏 | 视方案 | 沿用本地偏好则无需服务端；要求跨设备一致则需要服务端 |
| 定时任务 | 视方案 | 客户端定时发消息/生成既有待审批任务可无需新增；Hub 统一调度则需要服务端 |
| 图片/附件展示 | 基本不需要 | 现有消息和附件接口已支持附件元数据，主要改客户端展示 |
| 群记忆界面 | 基本不需要 | 服务端已有创建、检索、修订、删除和权限读取能力，主要是客户端接入 |
| 创建工作群表单 | 基本不需要 | 服务端已支持创建房间和名称；新增公告等初始字段时再涉及服务端 |
| 消息发送、回复、@ | 不需要 | 现有协议已具备 |
| 任务、审批、派发、撤销 | 不需要 | 现有主流程已具备 |
| 原群聊视觉复刻 | 不需要 | 属于 `application/` 客户端改造 |
| 解散权限本身 | 不需要 | 当前服务端已是群主和 Hub 管理端可解散 |

## 服务端核心修改结论

本次服务端最核心的硬修改是：

1. 工作群 Bot 成员关系；
2. 群公告；
3. Hub 管理端解散与群主解散的结果一致性；
4. 既有工作群 Bot 可见性的升级兼容。

不能把本次需求仅作为前端样式调整来排期。

# 边界情况

1. **拉入 Bot**
   - Bot 已在本群；Bot 属于其他成员且未授权；Bot 已下线；Bot 已删除；Bot 所有者已退出。
2. **创建**
   - 创建时没有选择 Bot；没有邀请任何真人；名称留空；创建过程中 Hub 断开。
3. **成员变化**
   - Bot 所有者被移除后，其 Bot 仍在群内；成员被移除时正在查看群；管理员与群主同时修改成员。
4. **解散**
   - 群主和 Hub 管理端同时解散；解散时存在待审批任务；成员正在输入；邀请待接受。
5. **消息**
   - Hub 断线、重连、重复消息、乱序、补拉失败。
6. **引用与定时任务**
   - 引用无权读取的会话；定时任务触发时任务已被解散；定时任务尝试直接执行远程 Bot。
7. **群记忆**
   - 成员被移除后检索旧记忆；群解散后访问记忆；记忆来源消息被删除。
8. **视觉验收**
   - 不同窗口尺寸、主题、语言、缩放比例下基础界面是否仍与原群聊一致。
9. **历史数据**
   - 旧工作群没有明确 Bot 成员关系；升级后当前可见 Bot 是否保留。
10. **Hub 管理端**
    - 管理端解散后客户端仍显示在线；管理端与客户端状态不同步。

# 异常行为

| 场景 | 用户应看到 | 系统应保持 |
|---|---|---|
| 拉入 Bot 失败 | 明确说明无权限、未授权或 Bot 不可用 | 不加入未授权 Bot，不泄露其他成员 Bot 的私人信息 |
| 拉入他人 Bot 未获同意 | 明确提示需要 Bot 所有者授权 | 不把 Bot 加入群，不允许 @ |
| 移除 Bot 失败 | 明确失败原因 | Bot 成员关系不变 |
| 创建失败 | 明确失败原因和重试入口 | 不产生半成品群 |
| 发送失败 | 保留草稿，标记未送达 | 不显示为已发送 |
| 引用被拒绝 | 明确说明无权引用 | 不泄露被引用会话内容 |
| 定时任务被拒绝 | 说明不能绕过审批 | 不执行远程 Bot |
| 群已解散 | 显示已解散和只读历史 | 禁止发送、邀请、改设置、发起任务 |
| Hub 管理端解散 | 客户端显示已解散 | 与群主解散结果一致，未完成任务取消 |
| 非成员访问 | 说明无权访问 | 不泄露群、消息、任务、附件是否存在 |
| Hub 离线 | 显示离线/重连中 | 本地普通群和私人聊天继续工作 |
| 视觉验收不通过 | 明确指出差异页面和差异项 | 不把“组件存在”当作“样式一致” |

# 保持不变

1. 原版普通群聊的创建、聊天、成员、@Bot、设置、附件、引用、群记忆、侧栏和删除/归档。
2. 原版普通群聊的历史数据和本地数据位置。
3. Chief、下属 Bot、私人聊天、模型选择、权限、工作目录和详情面板。
4. DSH 一级导航结构：插件入口原位置，只保留一个 Bot 一级入口。
5. 工作群现有安全边界：只有 Bot 所有者本人可审批；未批准不执行；撤销后不继续执行。
6. 工作群解散后历史保留的规则。
7. 既有工作群数据升级后不丢失。
8. Hub 独立部署方式，以及普通群聊不依赖 Hub 的现有行为。
9. 私人 Bot 记忆、私人 Session、普通群历史不自动并入工作群。
10. 普通群聊与工作群不共享会话身份、成员权限或历史数据。
11. 原群聊的代码、样式、行为和测试保持不变；工作群专属改动只进入复制后的工作群实现。

# 非目标

1. 不重做 DSH 或 DS Bot 整体设计。
2. 不把普通群聊改造成工作群，也不合并两种群实体。
3. 不设立可以代替 Bot 所有者审批的 Bot 管理员。
4. 不把原群聊的群级工作目录、群级权限直接变成工作群跨用户共享执行权限。
5. 不自动执行远程 Bot 轮次，不允许 @ 直接跨设备执行。
6. 不允许定时任务绕过审批直接执行。
7. 不把私人 Bot 记忆、私人 Session 或普通群历史自动导入工作群。
8. 不新增公网、SSO、移动客户端、端到端加密或公开社交能力。
9. 不对 Hub 运维管理端做整体视觉重做；但其工作群状态和解散结果必须与客户端一致。
10. 不通过修改原群聊代码、原群聊样式或原群聊群聊组件来适配工作群；工作群必须使用复制后的独立实现。若共享基础设施确需调整，必须证明不会改变原群聊行为，且不属于原群聊代码复制范围。

# 需求冲突

**无未决需求冲突。**

本轮已明确以下裁决：

1. **原群聊本地执行机制 vs 工作群安全**
   - 原群聊的自动轮次、@ 直接执行、群内工具读取本机等，不能跨用户照搬；
   - 按工作群优先，改为待审批任务、任务进度、任务取消和受权限控制的群记忆。

2. **原群聊管理员 Bot vs 工作群角色**
   - 原群聊管理员是 Bot；
   - 工作群不设可代替所有者审批的 Bot 管理员；
   - 工作群管理由人类群主/管理员承担，Bot 只是成员。

3. **原群聊群级工作目录/权限 vs 工作群审批**
   - 工作群不设跨用户共享的群级执行目录和群级执行权限；
   - 目录、工具和接收人由 Bot 所有者在任务审批时确定。

4. **原群聊创建时选成员 vs 工作群邀请**
   - 工作群真人成员必须通过邀请并接受；
   - 创建者可先建群，再邀请成员；
   - 创建流程的视觉和结构复刻原群聊，但成员关系按工作群模型执行。

5. **原群聊删除/归档 vs 工作群解散**
   - 工作群使用“解散”，历史保留；
   - 仅群主和 Hub 管理端可解散。

6. **原群聊基础界面 vs 工作群专属元素**
   - 原群聊已有界面必须一模一样；
   - 工作群新增的审批、任务、Hub 状态等元素按原群聊风格类似扩展。

# 验收标准

> 以下验收以当前仓库原版群聊代码为基线。

## AC-01 原群聊能力清单完整

**Given** 当前仓库原版群聊代码  
**When** 逐项建立工作群能力对照  
**Then** 每一项原群聊功能都有明确结论：直接复刻、工作群适配、或按工作群优先替换；不存在未检查或静默缺失项。

## AC-02 入口与会话行

**Given** 用户进入 Bot 内部  
**When** 打开新建菜单或查看群会话列表  
**Then** “创建工作群聊”位于“创建群聊”正下方；工作群不出现在 DSH 一级导航；工作群会话行与原群聊会话行在视觉和交互上一致，并显示工作群标识和 Hub 状态。

## AC-03 创建工作群

**Given** 用户选择创建工作群  
**When** 填写名称并完成创建  
**Then** 创建界面与原群聊创建界面一致；名称可填写；创建者成为群主；成员按邀请模型加入；自己的 Bot 可直接选择；创建成功后打开工作群；不再只生成日期名称。

## AC-04 基础界面一模一样

**Given** 相同窗口尺寸、缩放、主题、语言、字体渲染环境以及等价数据  
**When** 对比原群聊与工作群的基础界面  
**Then** 会话行、消息气泡、消息历史、输入区、成员区、设置页、详情页、空/加载/错误状态、悬停/聚焦/禁用状态和确认弹窗在视觉上一致。

## AC-05 消息与输入

**Given** 工作群已有成员和消息  
**When** 用户发送、接收、回复消息  
**Then** 消息按顺序展示；发送失败保留草稿并标记未送达；重复发送不产生重复；图片和附件按原群聊方式展示。

## AC-06 `+` 菜单

**Given** 用户打开输入区 `+` 菜单  
**When** 选择添加文件、引用会话或定时任务  
**Then** 入口和交互与原群聊一致；引用他人私人会话默认拒绝；定时任务不能绕过审批直接执行远程 Bot。

## AC-07 拉入和移除 Bot

**Given** 工作群成员管理界面  
**When** 用户拉入自己拥有的 Bot  
**Then** Bot 出现在成员列表，可被 @，显示所有者；  
**When** 用户尝试拉入其他成员的 Bot  
**Then** 必须取得 Bot 所有者授权，未授权时不能加入；  
**When** 移除 Bot  
**Then** 该 Bot 不再可被 @，不再接受新任务。

## AC-08 成员与角色

**Given** 真人被邀请加入工作群  
**When** 其接受邀请  
**Then** 成为成员并可访问群内容；非成员不能访问；被移除成员立即失去访问权；群主/管理员可管理成员；管理员不能解散；普通成员不能管理。

## AC-09 群设置

**Given** 有管理权限的用户打开工作群设置  
**When** 修改群名称、公告、侧栏状态、成员或 Bot  
**Then** 设置界面和交互与原群聊一致；公告、置顶/隐藏等原群聊功能可用；  
**When** 查看“谁应答”“工作目录”“权限”等设置  
**Then** 按工作群模型呈现，不得产生跨用户共享执行权限，不得出现可代替所有者审批的 Bot 管理员。

## AC-10 群详情、成员工作状态与群记忆

**Given** 用户打开工作群详情  
**When** 查看群概览、成员、工作状态、停止成员工作、用量和群记忆  
**Then** 页面结构与原群聊一致；停止成员工作映射为任务取消/授权停止；群记忆可检索、修订、纠错和按权限删除。

## AC-11 远程 Bot 审批

**Given** 成员 A 在工作群 @ 成员 B 的 Bot  
**When** A 发出请求  
**Then** 只生成待审批任务，不执行 B 的模型或工具；只有 B 本人可以批准/拒绝；群主、管理员和其他成员不能代批；B 可选择已有 Bot、Chief 自动选择或新建 Bot；撤销后新的执行被拒绝。

## AC-12 任务状态与成果

**Given** 已批准的工作群任务  
**When** 执行、取消、复核和分享  
**Then** 状态转换符合任务状态机；群内只出现脱敏进度；终态任务不能恢复执行；成果只分享给批准范围内的人。

## AC-13 解散权限与结果

**Given** 工作群群主或 Hub 管理端管理员  
**When** 执行解散  
**Then** 工作群进入已解散状态；待处理邀请撤销；未完成任务取消；历史保留并可只读访问；不能继续发送、邀请、改设置或发起任务；  
**Given** 工作群管理员或普通成员  
**When** 尝试解散  
**Then** 被拒绝。  
**Given** 群主解散与 Hub 管理端解散  
**Then** 两条路径的业务结果完全一致。

## AC-14 Hub 离线与恢复

**Given** Hub 不可达  
**When** 用户继续使用应用  
**Then** 普通群聊、私人聊天和本地 Bot 继续工作；工作群显示离线；未确认送达的消息不显示为成功；重连后按顺序补拉且不重复。

## AC-15 原群聊回归

**Given** 用户使用原版普通群聊  
**When** 执行创建、聊天、@Bot、成员、设置、附件、引用、群记忆、置顶/隐藏和删除/归档  
**Then** 所有原有行为、样式、权限和历史数据保持不变。

## AC-16 既有工作群数据升级

**Given** 系统中已有工作群、消息、成员、Bot 可见性、任务、审批和群记忆  
**When** 升级到新版本  
**Then** 历史数据完整保留；当前已可见的 Bot 不静默消失；新的 Bot 成员关系、UI 和专属能力正常工作。

## AC-17 专属元素视觉一致

**Given** 工作群出现审批卡、任务进度、Hub 状态、Bot 所有者标识等专属元素  
**When** 用户浏览工作群  
**Then** 这些元素与原群聊使用同一套设计语言、间距、字体、颜色和控件风格；不存在独立的视觉体系；用户仍能明确识别当前是工作群。

## AC-18 复制后独立演进，原群聊代码不改

**Given** 工作群功能、样式和专属能力已经实现  
**When** 对比原群聊代码与工作群实现  
**Then** 工作群基于原群聊代码复制件独立实现；原群聊代码、样式、行为和测试没有被工作群改造修改；工作群专属逻辑没有以条件分支侵入原群聊代码。
