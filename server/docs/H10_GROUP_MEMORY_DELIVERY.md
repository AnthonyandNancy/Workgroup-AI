## 关键设计决定

### 1. 两条独立检查：成员资格 + 条目作用域
读取路径先查 `room_members`（`removed_at IS NULL`），再查条目自身的 `acl_json.scope`。

**为什么是两个：** 一个 `room` 作用域的条目是"给这个群的"，不是"给任何知道它 id 的人的"。测试 `a room-scoped entry is still not readable by a stranger` 固定这点。

### 2. 非成员的一切访问都是 404，不是 403
知道 roomId 或 memoryId 不构成任何许可。真实验证确认：非成员读**真实 id** 与**伪造 id** 的响应**逐字节相同**。

### 3. 开发中被测试暴露的真实缺陷：删除路径泄漏了条目存在

`deleteMemory` 最初先判断"是不是作者/管理员"，陌生人因此得到 **403 `NOT_ALLOWED_TO_DELETE`** —— 这告诉了他"这条记忆存在"。

**修复：** 成员资格检查**前移**到权限判断之前，非成员直接 `requireMember` 抛出，路由转成 404。

**这个缺陷值得记录：** 我在读路径上都做了 404 处理，却在删除路径上漏了。**同一条规则要覆盖全部入口，不能只覆盖"读"**。

### 4. 可见性过滤在 SQL 里，不在 LIMIT 之后
```sql
WHERE room_id = ? AND deleted_at IS NULL AND lower(body) LIKE ?
  AND (expires_at IS NULL OR expires_at > ?)
  AND (author_user_id = ? OR json_extract(acl_json, '$.scope') = 'room')
LIMIT ?
```

**为什么：** 若在 `LIMIT` 之后过滤，5 条作者私有 + 1 条共享、页大小 2 时，成员只能拿到 1 条而**无法翻页获取更多**——看起来是"只有 1 条"，实际是查询截断。测试 `a page is filled with visible entries` 直接驱动这个反例。

### 5. 纠错只属于作者，管理员也不行
`reviseMemory` 检查 `author_user_id === editorUserId`。**即使把对方提为 admin，也不能改写他人的原话**（测试固定）。理由：群记忆的价值在于"谁说过什么"，让管理员改写会破坏这个属性。

管理员可以**删除**他人的条目，但审计里记为 `memory.deleted_by_admin` 而非伪装成作者操作。

### 6. 删除是时间戳 + 清空正文，不是删行
- `body` 清空 → 后续读取不可能泄漏已删除内容
- `acl_json` 收窄为 `{scope:'author', deleted:true}` → 即使有查询漏判也不会返回
- 行、修订轨迹、审计全部保留

**轨迹保留是关键：** 群在争论"当时决定了什么"时，需要看到"某条被修正过、然后被删除"这个**事实**。真实验证确认删除后轨迹仍可读。

### 7. 过期不是删除
到期条目不再出现在列表与搜索里，但 `deleted_at` 仍为 `null`——"失效"与"被撤回"是两件不同的事，审计需要区分。

### 8. 检索是字面子串，未声称语义检索
`lower(body) LIKE '%needle%'`。**不使用模糊搜索、不同义词、不排名**——调用方得到的就是它字面要的。语义检索未实现也未被声称。

### 9. 审计不含正文
`memory.created` / `memory.revised` / `memory.deleted` 的 `safe_details_json` 只有 `{roomId, scope, revision}`。审计是另一套更长保留期的存储，把正文复制进去会让"删除记忆"永远无法真正生效。测试断言正文不出现在审计里。
